# iMES 测试、问题修复与回归测试汇总报告

## 1. 文档目的与统计口径

本报告汇总以下三份原始报告的已执行结果，不替代原报告中的逐条断言、脚本结果文件和代码证据：

- [Net后端单元测试报告](./主流程、Workflow和Net后端测试报告/Net后端单元测试报告.md)
- [主流程与WF测试汇总报告](./主流程、Workflow和Net后端测试报告/主流程与WF测试汇总报告.md)
- [Vue前端单元测试报告](./Vue前端单元测试报告.md)

统计应按层级理解，**不能把不同时间、不同基线及存在覆盖重叠的数量直接相加**：

| 测试层级 | 目的 | 结果口径 |
| --- | --- | --- |
| 后端单元测试 | 隔离数据库、Redis、HTTP，验证实体、服务、控制器和规则契约 | 各测试工程最终一次复测结果 |
| Vue 单元测试 | Mock HTTP/浏览器/组件上下文，验证前端函数、组件和 extension 规则 | 当前整合后全量 `npm run test:unit` 结果 |
| 主流程/WF/API 回归 | 连接真实 API 和数据库，创建临时夹具验证跨模块链路 | 各专项脚本及通用回归的实际执行结果 |
| 交付差异 | 确认交付包没有对应实体、接口、页面或表，无法建立测试实例 | 不计为通过，也不伪装为测试失败 |

本轮数据权限/数据隔离不在范围；已验证的权限范围是目录、菜单、按钮、角色与操作审计。

## 8. 装配工单统计字段治理建议

### 8.1 当前数据职责

`Production_AssembleWorkOrder` 不是模板，而是装配工单的正式单据头：单据编号、备注、创建人与创建时间等基础字段应以主表为准。`WorkOrderQty`、`FinishedQty`、`FormProcess` 虽然历史上也存在于主表，但当前业务未在明细新增/删除、工单完成或状态回退时同步维护，已确认其值长期为 `NULL`，不能作为统计查询依据。

实际业务数据关系如下：

```text
Production_AssembleWorkOrder（单据头）
        + Production_AssembleWorkOrderList（工单明细）
        + Production_WorkOrder（实际执行/完成状态）
        ↓
GetAssembleProcess（实时统计视图：工单数、已结束工单、进度）
```

视图不是另一份人工维护的数据，而是数据库依据明细和生产工单实时计算出的读取模型。因此当前装配工单列表的正确口径为：主表提供单据基础信息，`GetAssembleProcess` 提供实时统计信息；二者按 `AssembleWorkOrder_Id` 关联后，再统一筛选、排序、分页和显示。

### 8.2 已采取的低风险治理措施

AWO-FIX-01 已使装配工单列表不再依赖主表内三个旧统计列：`工单数`、`已结束工单`、`进度` 的显示和数字搜索均使用 `GetAssembleProcess` 实时统计结果。主表旧列暂时保留，以避免影响现有实体、页面配置、历史脚本或外部报表。

### 8.3 后续建议

建议将主表中的 `WorkOrderQty`、`FinishedQty`、`FormProcess` 明确标记为废弃字段，并逐步排查其他接口、报表和 SQL 是否仍读取它们；新功能不得再写入或以其作为统计条件。待确认不存在外部依赖后，再通过数据库迁移删除旧列并重新生成实体/页面配置。

不建议当前直接删除列：这属于破坏性数据库兼容变更，可能影响历史脚本、代码生成配置或第三方报表。另一条可选路线是将这些列重新定义为“缓存汇总”，但那要求在新增/删除明细、工单完工、撤销/回退等全部状态变化中以事务同步更新，维护成本高且容易再次出现展示与搜索不一致；在现有已具备实时视图的前提下，不推荐采用该路线。
