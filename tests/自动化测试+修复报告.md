## 修复与复测（2026-07-14）

### 修复原因和依赖注入逻辑

`Sys_DictionaryListService` 是实现 `ISys_DictionaryListService` 的服务类。接口请求到达 `Sys_DictionaryListController` 时，Autofac 需要先创建这个服务类。

修复前，服务构造函数又要求 Autofac 注入一个 `ISys_DictionaryListService`。由于该接口仍然对应当前这个服务类，依赖链变成：

```text
创建 Sys_DictionaryListService
  -> 需要 ISys_DictionaryListService
  -> 仍需创建 Sys_DictionaryListService
  -> 循环依赖，服务无法创建，接口返回 HTTP 500
```

这不是字典数据缺失，也不是字段需要设置默认值；它是一个未使用的服务依赖声明错误。

### 具体改动

在 [Sys_DictionaryListService.cs](/Users/yuanzhuoshen/Desktop/MES系统源码Docker部署/源码/iMES.Net/iMES.System/Services/System/Partial/Sys_DictionaryListService.cs:19) 中删除了三处未使用的自引用内容：

```csharp
// 1. 删除字段
private readonly ISys_DictionaryListService _dicListService;

// 2. 从构造函数参数中删除

// 3. 删除构造函数中的赋值

```

保留了实际使用的三个依赖：字典明细仓储、字典主表仓储和 `IHttpContextAccessor`。因此业务查询逻辑、字典数据和默认值都没有改变。

## Docker 重启后前端请求失败排查（2026-07-15）

### 现象与原因

本次未改动应用源代码、Docker Compose 配置或 Redis 配置。问题发生在手动停止、再选择性启动容器之后，分为两个阶段：

| 浏览器表现 | 实际原因 | 已处理结果 |
| --- | --- | --- |
| `net::ERR_CONNECTION_REFUSED`，请求 `localhost:9991` 失败 | 仅启动了 `sqlserver-x64` 和 `redis`，`api` 容器没有运行 | 启动 `api` 后，9991 端口恢复监听 |
| 菜单接口 HTTP 500，响应文本为“服务器没有正确处理请求” | API 日志显示 CSRedis 连接池报 `Connection was not opened`，发生在读取当前登录用户缓存时 | 验证 Redis 认证和网络正常后，重启 API 以重建其连接池 |

`sqlserver-x64` 是 `x64-sqlserver` profile 服务。普通的 `docker compose down` 不带 profile 时不会停止它，所以会看到网络仍被 `mesdocker-sqlserver-x64-1` 占用；这是预期行为，不是额外未知容器。

### 排查与验证

已完成以下检查：

1. `redis` 容器状态为 `healthy`，使用当前配置密码执行 `PING` 返回 `PONG`。
2. API 容器已接收到 Redis 连接配置，且能解析 `redis` 容器地址并连通 `redis:6379`。
3. 在 API 容器中使用其自身已注入的 Redis 配置执行 `AUTH` 和 `PING`，均返回 `+OK`、`+PONG`。
4. 重启 API 后，未登录请求 `GET /api/menu/getTreeMenu` 返回规范的 `401` JSON，而不是 HTTP 500；新的 API 日志中没有新的 Redis 连接异常。

### 当前操作步骤

推荐一次启动完整 Docker 服务：

```bash
docker compose --profile x64-sqlserver up -d
```

若只启动数据库和 Redis，则 API 不会自动运行：

```bash
docker compose --profile x64-sqlserver up -d sqlserver-x64 redis api
```

本次执行的是不带 `-v` 的 `docker compose down`，命名卷 `mssql-data`、`redis-data` 没有删除，所以无需重新导入数据库。只有使用 `docker compose down -v` 或手动删除 `mesdocker_mssql-data` 后，才需要重新导入数据库。

### 登录态说明

API 容器日志提示 Data Protection 密钥未持久化。容器重建后，浏览器原有登录态可能无法继续使用。若 API 已正常运行但页面仍请求异常，先强制刷新；仍不恢复时在浏览器控制台执行：

```js
localStorage.clear();
sessionStorage.clear();
location.reload();
```

随后重新登录。上述处理只清除浏览器本地登录状态，不删除数据库或 Redis 中的业务数据。

### 系统行为说明

销售订单的“自动生成”和“自动拆分”不是两个独立 API 操作。`Production_SalesOrderService.Add` 在保存销售订单时，直接创建 `Production_WorkOrder`，并根据产品的 `Process_Id` 调用工艺路线查询，生成 `Production_WorkOrderList` 任务。因此该测试以一次销售订单新增操作验证了这两个环节的真实业务实现。

完工时，`Production_WorkOrder/changeUpdate?status=3` 使用 `View_OutputStatistics` 汇总**工艺路线最后一道工序**的报工数量；本轮两道工序均有报工，最后一道工序良品数为 7，因此工单汇总为 7。入库模块的库存统计来自 `View_GetProductStoreNumber` 对入库、出库明细的计算，而不是直接更新 `Base_Product.InventoryQty` 字段。
